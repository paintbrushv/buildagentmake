# Reproducible measurement and pending human baseline

**HackFW status: submitted; presentation materials ready for Friday, October 30, 2026.** See the [submitted entry](https://devpost.com/software/forgepath-supplier-desk), [public video](https://vimeo.com/1239320256) and [Demo Day plan](../DEMO_DAY.md). Submission completion does not change the unmeasured human-baseline status documented here.

The checked-in results measure local deterministic core execution on synthetic data. They do not measure operator task completion, browser performance, spreadsheet time, supplier discovery on the web, or commercial adoption. Scenario eligibility is fixed at **2026-10-21**, regardless of the machine's current date.

## Reproduce the measured software work

From the project root, run:

```sh
node scripts/benchmark.mjs
node --test test/benchmark.test.js
```

Node 18 or later is sufficient; no dependency installation is required for the benchmark. The first command overwrites `validation/benchmark-results.json` and `validation/benchmark-report.html` with results from the current machine. Retain the original JSON separately before rerunning if comparing machines. No numerical latency target is asserted.

`benchmark-results.json` identifies itself as `kind: "deterministic-core-benchmark"`. It records the actual measurement timestamp, fixed scenario date, Node/OS/CPU environment, 100 warmups, 1,000 measured iterations per task, every raw core and setup sample, median, p95, and individual file hashes. A combined SHA-256 hashes, in listed order, each relative source path, a NUL byte, its exact bytes, and another NUL byte. The hashed sources are `domain.js`, `scenarios.js`, `scripts/benchmark.mjs`, and `validation/fixtures.json`. The report is generated directly from that JSON-shaped result; it does not contain separately entered measurements. Results are checked before and after timing.

| Task | Exact work within one core timing | Setup outside core timing |
| --- | --- | --- |
| Intake → discovery | Analyze the one labeled card; onboard the confirmed extracted fields with original-text provenance; search by exact manufacturer name; compute its clevis match | Fresh `makeSeed()` |
| Requirement → shortlist | Score all 4 seed suppliers against all 4 requests using 6 gates; form each ready list; order ready suppliers by score then ID | Fresh `makeSeed()` |
| Review → packet | For each of the 4 requests: select request, record the specified synthetic named advance/hold decision, build its supplier review packet snapshot and comparison, serialize packet HTML | Fresh `makeSeed()` |

All three numbers are **batch latencies for the work shown**, not per-field or per-supplier times. `makeSeed()` clones fixture requirements/suppliers and initializes state; its samples are recorded separately. Cloning performed inside production onboarding or packet construction is part of core timing. File reads, correctness assertions, source hashing, JSON/report writes, browser DOM/rendering/download, and operator reading/typing are outside the core timer. The output count is consumed after each timer to retain measured outputs. Execution is synchronous in one Node process. No garbage collection is forced and no timer overhead is subtracted. Percentiles use nearest rank, `sorted[ceil(n × p) − 1]`; the median is p50 under this convention. Millisecond precision in JSON does not imply equivalent practical timer accuracy.

This tiny in-memory test is sensitive to machine speed, scheduling, timer overhead, JIT and garbage collection. Warmups reduce first-run effects but do not remove those limitations. The review-packet task is the supplier decision and review packet workflow; the separate RFQ response-event lifecycle is outside this benchmark.

## Fixed inputs and independently specified answers

`fixtures.json` is the shared input/output contract. Its flat `supplierRows` are a four-supplier worksheet reference independently transcribed from the synthetic seed. `requests` states the required process, alloy/material, tolerance, quantity, qualification and U.S. site requirement. The explicit 16 comparison answers specify score, failed gate keys and readiness; they are not generated by the production scorer. The benchmark additionally implements a short worksheet-style **software** reference using these rows and its own criteria, with no production scoring/canonicalization/qualification calls. It checks both that reference and production outcomes against the explicit answers. It checks the worksheet source fields against the current seed so a source change cannot silently retain a stale comparison.

| Request | Expected best ready supplier | Expected ready list |
| --- | --- | --- |
| Camera mounting bracket | SUP-DEMO-001 | SUP-DEMO-001 |
| Electronics stack standoffs | SUP-DEMO-002 | SUP-DEMO-002 |
| Electronics isolation tray | SUP-DEMO-003 | SUP-DEMO-003 |
| Landing-gear clevis | None | Empty |

There are 16 seed supplier/request pairs: 3 expected ready and 13 expected blocked. The recorded zero false-ready and zero false-blocked counts apply **only to these 16 explicit pairs**. They do not establish accuracy on unseen suppliers, extraction language or real certificates. The single new-card intake is checked separately: it is searchable, has no qualification records, stays self-reported, and remains blocked for clevis by `qualification` and `domestic` (unreviewed site). No external source is retrieved.

Red River's AS9100D evidence expired on 2026-10-01. At the fixed 2026-10-21 scenario date it fails the clevis qualification gate even though process, material, tolerance, quantity and site checks pass (90/100 fit score). Attempting to advance it throws. Prairie's AS9100D record awaits review and also blocks. A high score never substitutes for all required gates passing.

The four packet assertions compare request/supplier identity, decision action and current status, named synthetic reviewer, expected packet status and the entire comparison matrix. The three ready requests use `advance`; clevis uses `hold` on SUP-DEMO-002 and stays `Review only — approval required`. These are automated synthetic records, not evidence of a person having reviewed a real supplier.

## Matched human worksheet comparison protocol — not yet run

**Status: participants n=0; completed timed human trials n=0.** There is no measured manual spreadsheet time, improvement percentage, hours saved, ROI, or adoption figure. The software reference must never be presented as a timed human/manual baseline.

[HUMAN_TEST.md](HUMAN_TEST.md) is the authoritative observer script, timing procedure, participant-assignment plan and error rubric for the future human comparison. Both arms use the same synthetic source facts and readiness rules, the same four suppliers and requests, the same one intake card, and the fixed 2026-10-21 scenario date. The worksheet Facts sheet excludes `expected*` answers. Do not expose the fixture JSON, benchmark report or results to participants before both arms end: these include the answer key. Raw fixture rows retain the capability source ID/label/observation date, site ID/source/reviewer/review date, and each certificate source reference/site ID/observation/review date, status, validity, scope and reviewer so both arms can inspect equivalent information.

The human comparison has three separately timed tasks:

| Human task | Comparable required output |
| --- | --- |
| Intake and find | Preserve all supplied card facts and evidence status in a new profile; find it by manufacturer name. The new profile stays outside the next task's four-supplier comparison. |
| Shortlist | Ready/not-ready decision and exclusion reasons for all 16 supplier/request pairs, with ready suppliers grouped by request. A numeric match score is not required in the worksheet arm. |
| Named camera-bracket review packet | One camera mounting bracket packet with request/drawing revision, selected supplier, capability and qualification/domestic evidence, source references, decision/rationale/open issues, reviewer name, review time and packet status. No RFQ is sent. |

The **four-packet software benchmark** above checks a broader batch of core outcomes. It must not be described as the human task workload or used as a human completion-time denominator. Human task 3 requires **one bracket packet only**. Allow the worksheet packet to remain in cells or be saved/printed normally; corresponding product output may be retained as HTML/JSON. Do not impose an export-format penalty on the manual arm.

Exclude technical setup in both human arms. Reset to a fresh fixture before each condition. Read each task statement verbatim from HUMAN_TEST.md, then start that task's timer only after the participant says they are ready. Stop when they declare completion and present the output, abandon it, or reach the same predeclared budget. Include mistakes, assistance and waits within task timing; record interruptions separately. Record per-task start/end timestamps and elapsed seconds, completion, errors, help requests, failures and notes. Unobserved cells stay blank. Preserve incomplete and assisted results with their status, rather than treating them as zero or silently dropping them.

Use people who did not build or debug the product or answer key. Counterbalance arm order as specified in HUMAN_TEST.md; optional untimed practice uses a different example and is offered equally. Save outputs before revealing the key, and score both arms against equivalent fields/readiness/reasons, preferably with a separate assessor. Report actual sample size, order, familiarity and learning limitations alongside time and correctness. No four-task synthetic study can establish general annual savings, financial ROI, production accuracy or adoption. Keep local core software latency separate from participant wall-clock observations.
